# UniBuzz technical reference

> This is the detailed reference that was the repository README until 2026-10-25, kept as it was apart from its opening description, which now puts the social network first. It describes each feature's design, the database migrations and their rollout order, and setup from scratch. The project began as "Apartment Book", which is why that name still appears below and in package names. For an overview, start with the [README](../README.md).

**A private social network for university life — connecting students, clubs, events, campus news, housing, and the student marketplace in one place.** At its core, students **share posts, reels and anonymous Buzz threads** on Home and **message each other** in private, group and class chats. Explore adds the supporting tools for student life: **apartments near campus**, **roommates**, and a **marketplace** for move-in essentials (mattresses, desks, kitchen gear…). The layout follows the Facebook pattern: a top bar with three tabs (Home, Explore, Messages) plus the search box, a create menu and a profile menu; on phones the bar is Home, Explore, Messages, Profile at the bottom of the screen (the app's bar is Home, Explore, + (create), Messages, Profile, with Search and a Notifications bell that opens every notification in Home's top-right corner). Search finds people by name first (with a Follow button on every result), then apartments, roommates and items. Home itself has three top tabs, For you | Buzz | Reels (in the app under a UniBuzz wordmark, Instagram style; Posts is a fourth section that keeps its feed and its `/?tab=posts` address on the website but has no tab), see [Home feed](#home-feed); the Explore tab holds Housing (apartments), Roommate and the Marketplace side by side, see [Housing](#housing).

Built with **Next.js 16 + TypeScript + Tailwind** on top of **Supabase** (Postgres, auth, realtime chat, image storage). The backend is a hosted service that iOS/Android apps can talk to directly, and all data-access code lives in a shared package, so the future mobile app reuses everything except the screens.

Group chats keep "N members". Who is online comes from Supabase Realtime Presence on a private channel, `presence:active` (`PRESENCE_TOPIC`), that only signed-in people who show their activity status may join (the green dots on avatars, the app's online friends row and Roommates' Online now come from it too, leaving out people blocked either way, from `blocked_either_way_ids()`). The app going to the background stamps the time and stops appearing there at once (no timer runs in the background on a phone, so a grace would last until the server dropped the silent connection); a hidden browser tab does the same 15 seconds later on a computer (a quick look at another tab changes nothing for anyone), and at once on a phone or tablet or when the browser freezes the page. Back in front, they stamp first and appear once that stamp confirms the status is still shown; after a dropped connection that outlasted the last stamp they stamp again before appearing; in front, the time is stamped and the block list read again every minute. Logging out leaves the channel at once. Exact last-active times live in `user_activity`, a table the API can neither read nor write: `activity_status()` answers only while you show your own status (hide yours and you see nobody's), they show theirs and neither of you has blocked the other: for anyone you share a chat with, whether they are recent (so "Active now" can show, as their green dot does anyway), and their time, cut to the minute, only once they have written to you in a chat you are both in, since you joined it (an empty chat, a group someone made with everyone, or what a group said before you joined is not enough). "Active now" needs presence and a recent stamp both, since anyone on the channel could claim presence for someone else. Settings → "Show your activity status" turns it off: it deletes your time, and your devices stop marking messages "Delivered" (people see "Seen" once you read something new). Only that switch turns it back on (`set_show_active_status()`), so a stale Settings save from an installed old build cannot undo a hide. Migration 22 (`supabase/migrations/20261011000000_activity_status.sql`) adds the table, the `touch_activity()`, `activity_status()`, `blocked_either_way_ids()` and `set_show_active_status()` functions and the Realtime Authorization policies of the channel, retires the public `profiles.last_seen_at` (emptied and never written again; old builds still read it), makes `mark_delivered_all()` do nothing while you hide your status and `mark_conversation_read()` change nothing when there is nothing new to read (opening a chat no longer tells its members when you had the app open), dates every message no later than when it is sent (one dated ahead used to stay "new" and keep "Seen" and "Delivered" moving), lets chat members change only their own receipts and a group's name (no moving a membership into another chat, no turning a direct chat into a group), lets a notification be changed (`read_at` only) or deleted only once it shows, and grants `profiles` and `notifications` to the API column by column so their system columns (`xmin`, `xmax`, which traced who wrote or locked a row and when, down to anonymous Buzz replies and when they were made) are unreadable. The labels live in `packages/shared/src/activity.ts`, the presence store and the queries in `packages/shared/src/queries/presence.ts` |

## Photos: full quality, built to hook

Photos are the product, so the pipeline never degrades them:

- **Originals are stored untouched.** The browser uploads the exact file to Supabase Storage (JPG, PNG, WEBP, GIF or HEIC, up to 25 MB each, up to 12 per listing). Nothing is resized or re-encoded on upload.
- **Sharp on every screen.** Feeds and detail pages render through Next.js image optimization at quality 85 to 90 in AVIF/WebP with a size chosen for the viewer's screen (`images.qualities`, `deviceSizes` and `formats` in `apps/web/next.config.ts`). The full-screen viewer shows the original file itself, and its "Original" button opens it directly.
- **No blank boxes.** At upload time the browser reads each photo's dimensions and builds a tiny blurred preview (about 1 KB) that is saved as `image_meta` next to the listing. Feeds show the blur instantly and fade in the real photo, and layouts never jump.
- **Instagram-style feed.** Cards are photo-first with swipeable multi-photo carousels, a photo counter and dots, price overlaid on the photo, a bookmark button, and double-tap to save with a burst animation. Feeds load more as you scroll ("You're all caught up" at the end) and open with a stories-style strip: closest to campus on Home, fresh finds on Marketplace.
- **Detail pages.** Swipeable hero, thumbnail strip, and a full-screen viewer with swipe, arrow keys, double-tap zoom and the original download.
- **Uploader.** Drag and drop or pick files, instant previews while uploading, per-photo progress and errors, reorder, and "Make cover".

Vercel's Hobby plan optimizes up to 5,000 distinct source images per month. If the site outgrows that, upgrade the Vercel plan or move rendition generation to Supabase image transformations (Pro plan).

## Notifications

A `notifications` table that only its recipient can read, mark or delete; rows are created by database triggers so the mobile app gets them for free: a new message (repeated messages in one chat refresh a single unread entry; it rides along for the push but shows only in Messages, see below), someone saved your listing, someone started following you (one entry per follower, however often they follow and unfollow), someone replied to your comment, someone sent you a Snap (one entry per chat until it is read, see [Snaps](#snaps)), a call you missed (`call`, see [Calls](#calls)), and a new place pinned within 2 miles of your campus (opt-in per person in Settings). The top bar shows a bell with a live count and dropdown; `/notifications` lists everything except new messages and Snaps, which belong to Messages alone (its unread counts and badges, and the push): `listNotifications()` and `getUnreadNotificationCount()` in `packages/shared/src/queries/notifications.ts` leave out `MESSAGE_NOTIFICATION_TYPES`, and since migration 37 so does `unread_notification_count()`. Since migration 36 (`supabase/migrations/20261029000000_push.sql`) every notification `notify()` makes also goes to the person's phones: `send_push()` posts it with pg_net to Expo's push service, to the Expo push tokens the app stores in `device_push_tokens` (a real device, signed in, with permission granted), with the notification's type and link as data so a tap opens the right screen; nothing is sent where pg_net is missing, and a push that cannot be sent never fails what it rides on. With Expo's enhanced push security turned on, put the project's access token in Vault as `expo_push_token` and it goes along.

## Snaps

A Snap is a photo or a video (up to 30 seconds) taken with the phone's own camera from the app's **+** menu (Post, Reel, Buzz (anonymous), **Snap**) and sent straight into the direct chats of the people you pick, each of whom can open it **once**. The camera opens over whatever is on screen; what it takes fills the screen on black (a photo over a blurred copy of itself) with close and "take another" at the top and the Aurora **Send To** at the bottom. Send To rises as a sheet with your direct chats (the most recent first) and your friends (people you follow who follow you back), and a search over them; pick up to 50 and the round send button shows the upload going up, then the paper plane flies off and a tick lands. Each person gets one message in your direct chat with them (the chat is made when there is none), the inbox reads "Sent a Snap", and a **snap** notification says "Sent you a Snap" (a muted chat stays quiet). A chat never shows a Snap's picture: it is a bubble at the Snap's own shape (the app draws it like a sent photo, the same size) showing only a tiny preview in its own colours (made on the phone when it is taken, from the photo or the video's first frame), softly visible under a light pane of frosted glass (colours and vague shapes, drifting slowly while the Snap waits to be opened, never a detail: the preview is 32 pixels on its long side), with "Tap to view" for its recipient and "Delivered" for its sender; tapping opens it full screen once (a photo until you tap, swipe it down or close it; a video plays through once with a bar along the top), and from then on both see "Opened" over the same blurred preview (in the app at seven tenths of the size): since migration 32 opening it leaves the preview on the message, while a Snap that goes unopened (it expires, or its sender's account goes) still loses it at once (migration 29). A Snap nobody opened within 31 days expires and both see "Expired". Under every Snap both sides see what happened to it, Snapchat style, with the time: delivered, opened, a screenshot or a screen recording (the sender is told at once with a `snap_activity` notification), all as the same quiet grey note, never a warning, deleted (the sender can take a waiting Snap back), expired; a tap opens the whole story, which stays after the Snap is over (`messages.snap.activity`, migration 33). The sender is never told more than the viewing phone can detect: an iPhone reports screenshots and blacks out recordings, an Android phone blocks both, and anything else reports that it can detect nothing. The website shows the same cards and says to open the app to view one.

The database enforces all of it (migration 28, `supabase/migrations/20261020120000_snaps.sql`). The files live in a private `snaps` bucket that no client can list, replace or delete: the sender uploads into their own folder, and a recipient can read a file only from opening it until they close it, two minutes at most (`open_snap()` / `close_snap()`), never after it expired and never twice; the app loads it through Storage's signed-in download with the viewer's own session, so every request is checked against that and no link outlives the view. The `snaps`, `snap_recipients` and `snap_purges` tables have no policies and no grants, and `messages.snap` is written only by `send_snap()` and `open_snap()` (a trigger refuses it from the API). `send_snap()` takes only friends and people you already have a direct chat with, nobody blocked either way. Every 10 minutes `purge_snaps()` (pg_cron) forgets every Snap that everyone has opened (10 minutes on), every Snap that expired and every file uploaded but never sent (an hour on), and deletes the files through the Storage API with pg_net, using the project URL and service key that `npm run db:setup` keeps in Vault; a file is checked off only once Storage no longer has it, and a chat whose Snap went unopened (it expired, or its sender's account was deleted) is told at once. The moment the last person a Snap went to closes it, `close_snap()` deletes its file itself (migration 30) rather than waiting for the purge. One thing the database cannot close: Supabase's CDN keeps serving a file it has handed out to the same person, under any of their sessions, for about a minute after the file is deleted (and until then for as long as it exists, whatever the policies say by now); nobody else can get it that way (the CDN checks who is asking; this was measured live on 2026-10-23). So with a tampered app the recipient who just watched a Snap could fetch the same bytes once more for up to a minute, and no one else ever can. The app keeps a viewed photo in memory only, never on disk.

## Calls

**Paused for now.** Until there is an Apple Developer Program membership no iPhone build can carry calls, so the app keeps every call button, call row and call screen but a tap shows a quiet "Coming Soon" notice under the chat's bar instead of ringing anyone: nothing is written to the database, no ring is listened for, and the Join banner stays hidden (`CALLS_PAUSED` in `apps/mobile/src/lib/calls.ts`). Everything below stays in place, deployed and tested (the database, the `livekit-token` function and its LiveKit secrets, the native modules and their config); a build bundled with `EXPO_PUBLIC_CALLS_ENABLED=1` turns calls back on. The rest of the app runs in Expo Go.

Audio and video calls, FaceTime style, in every chat: a direct chat rings one person, a group (a class group too) rings everyone in it, and anyone can join a call that is going on. The chat's top bar has **Audio call** and **Video call** beside Info; a call opens on its own dark stage with the other person's video (or their photo) filling the screen and your own camera in a small window, a grid for a group (the people it is still ringing faded, "ringing" under their names), their name and the call's standing at the top ("Calling…", "Connecting…", the running time) and a glass bar of controls along the bottom: mute, speaker, camera on and off, flip camera, the people in the call (a group), and the red End button. The caller hears a ringback; the phone being called rings and buzzes (respecting the silent switch) and shows a full-screen incoming call with the caller's photo and Decline / Accept over whatever is on screen; a ring that nobody answers within 45 seconds stops on its own and the call is missed. Every call is a row in the chat, the same on both sides and on the website, that follows the call live and reads, once it is over, "Audio call · 3:24", "No answer" (for the caller), "Missed video call" (for whoever did not pick up, in red, with a `call` notification), "Video call declined"; a tap on it calls back, or joins the call if it is still going on, and a glass pill under the chat's bar offers to **Join** a call going on in the chat that you are not in. Leaving the call screen in any way hangs up; when everyone else has left, yours ends too.

The database keeps every call and who stands where in it (migration 35, `supabase/migrations/20261028000000_calls.sql`): the `calls` and `call_participants` tables, readable only by the chat's members, written only through `start_call()`, `answer_call()`, `decline_call()` and `leave_call()` (`get_call()` and `current_call()` read them with the participants' names and photos); `messages.call`, the call's row in the chat, is written only by those functions (a trigger refuses it from the API) and updated as the call goes on, so the chats and the inbox preview follow it live over the existing realtime channel; a ring that was never answered is closed as missed by the next call anyone makes (`expire_stale_calls()`, 60 seconds on), and an active call left hanging is closed after 6 hours; the call's own message sends no "new message" notification, and only a missed call sends one (`call`, deduplicated per call). `supabase/tests/calls.test.mjs` runs all of it in PGlite (ringing, answering, declining, cancelling, the ring running out, a group where some decline and some join late, strangers and the API refused, the row's text on both sides); `packages/shared/tests/calls.test.mjs` the row's wording.

The sound and picture travel over **LiveKit** (WebRTC, end-to-end over DTLS-SRTP), one room per call named by the call's id. The `livekit-token` Edge Function (`supabase/functions/livekit-token/index.ts`) checks the caller's session, asks the database with `get_call()` that they are in the call (state `joined`) and mints a two-hour token for that room alone; without a token nobody connects, so the chat's membership rules are the call's. To set it up: make a LiveKit Cloud project (free tier at cloud.livekit.io; or run a LiveKit server), then `npx -y supabase@latest secrets set --project-ref dskbzoqreandwwpxiplh LIVEKIT_URL=wss://… LIVEKIT_API_KEY=… LIVEKIT_API_SECRET=…` with `SUPABASE_ACCESS_TOKEN` set (the function itself is deployed with `npx -y supabase@latest functions deploy livekit-token --project-ref dskbzoqreandwwpxiplh`, no Docker needed; the Dashboard's Edge Functions page takes the same file). Until the secrets are set the function answers "Calls aren't set up on the server yet." and the call screen says so. `SUPABASE_ACCESS_TOKEN=sbp_… node apps/mobile/e2e/call-lifecycle.mjs` runs the whole signalling lifecycle against the live project with throwaway accounts, asks the function to check its key pair against LiveKit (`{"check": true}` answers whether LiveKit accepted a server token, never a secret) and reports whether a call token can be minted, leaving nothing behind. The apps' media module (`@livekit/react-native`, `@livekit/react-native-webrtc`, with their Expo config plugins in `app.json`: microphone and camera permission texts, background audio, Android's communication audio mode and Bluetooth permissions; the camera text is written twice, as `ios.infoPlist.NSCameraUsageDescription` and as expo-image-picker's `cameraPermission`, and the plugin's is the one iOS shows, so the two stay the same: video calls, taking photos and recording videos) is compiled only into the app's own builds, never into Expo Go: in Expo Go calls still ring, answer and show their rows, but no sound or picture flows, and the call screen says the build cannot carry calls. Ringing reaches a phone over realtime while the app is open (and any ring still waiting is picked up when the app comes back to the front, within the 45 seconds); a phone whose app is in the background or closed is rung by a push (migration 36: `start_call()` sends "Incoming video call · Maya is calling" to everyone it rings, with the app's own ring sound on the Calls channel, dropped unseen once the 45 seconds are over), and tapping it opens the incoming call in the app if it is still ringing. That is a notification, not a system call screen: the full-screen native ring of a locked phone (iOS CallKit with PushKit, Android's full-screen intent) is not built, and would need an Apple Developer account's VoIP certificate. In a call, an iPhone keeps the sound going in the background (`UIBackgroundModes: audio`) and pauses the camera, as every app's does; an Android phone keeps it only as long as the system lets a backgrounded app use the microphone (newer versions cut it after a while without a foreground service, which is not built either). A refused microphone or camera does not end the call: the screen says to allow it in Settings.

## Events

Events is the fourth tab, with a calendar icon. It shows the campus's events in one place and lets people save them, share
them, register and follow the organizations behind them. Two pages sit under the title, **For you | All events**, with the
inbox's search box and one row of pills under them: the date pills (Upcoming, Today, This week, Weekend) and the category
pills (Academic, Career, Social, Sports, Music, Arts, Tech, Wellness, Cultural, Service, Faith, Other). Every time is shown on
the campus's own clock (`universities.timezone`).

**Where events come from.** Two sources only, so nobody can fill a campus's calendar on their own:

- **The university's calendars.** Staff add ICS or RSS feeds in the console (`/admin/events`, admins add and change feeds,
  every staff member can press Sync now). The website syncs them (`apps/web/src/lib/events-server/sync.ts`, called by
  `/api/events/sync` from Vercel Cron, daily on the Hobby plan, and by the console): it reads the calendar
  (`packages/shared/src/events/ics.ts`, `rss.ts`: folded lines, local and UTC times, all-day events, weekly and monthly
  rules, overrides, cancellations), plans the difference against what the database has (`events/sync.ts`: new rows,
  changed columns, future events the feed dropped marked cancelled, never deleted), skips an event another feed or an
  organization already lists (same title at the same moment on the same campus), guesses a category from the calendar's
  own words, and writes with the service role. A feed's event a staff member hid stays hidden through later syncs.
- **Organizations.** Any student can create a club, student organization or department and becomes its owner; owners
  add editors and other owners. Members publish and manage its events in the app. Until staff verify the organization
  (the console's Organizations section), its events are `pending`: its members see them, nobody else does. Verifying
  publishes them; unverifying or hiding the organization takes them back.

**What people do.** Save (the bookmark; `/events/saved`), share (the native share sheet with the website's address),
open the registration link, follow an organization, pick interests. Each of those feeds the ranking below. Opens,
registration taps and shares are counted once a day per person (`record_event_click()`); only the counts leave the
database, and a student reads only their own rows.

**For you.** One formula in code (`rankEvents`, `packages/shared/src/events.ts`), the same in the app and on the website,
deterministic: a picked interest (+3), the categories the person keeps saving and opening (up to +2.5), a followed
organization (+4), how soon it is (+3 tonight, half of that in a week), how many others saved or opened it, a picture, a
verified organization; a cancellation counts against. Among the first five rows one organization does not take a third
row in a row while something else scores within a point. The pills always apply on top. Signed out, time and popularity
alone.

**Staff.** `/admin/events` in the Trust & Safety console: the counts, the feeds (status of the last sync, its error, Sync
now, add, edit, delete), the organizations (verify, unverify, hide, restore, with a note) and the events (hide, cancel,
restore, with filters). Every change is an `audit_log` row (`organization.verify`, `event.hidden`, `event_feed.create` …)
written in the same transaction by the `events_console_*` functions, which answer non-staff "not found" and need
two-factor sign-in like the rest of the console.

**Multi-campus.** Every event, feed and organization belongs to a university; every university has a time zone; the
Events tab shows the signed-in student's campus (everything, signed out). A new campus is a seed row with its zone.

## Business portal

Since migrations 49 and 50 (UniBuzz Business v2: team roles, posts, the Ads Manager, Sponsored ads, business profiles,
analytics), the README's "UniBuzz Business v2" section describes what changed; what follows is v1, all of which still
holds.

**UniBuzz Business** is a website of its own for landlords and local businesses, served at `/business` on the main site, and at its own domain once one is set (`NEXT_PUBLIC_BUSINESS_SITE_URL`; none yet). It has its own login and sign-up but shares the backend and the auth with the student apps; there is no mobile app for it, and the student app shows a business account only a notice pointing to the portal.

- **Roles.** `profiles.role` is `student` (everyone so far), `business_owner`, `business_staff` or `admin` (migration 39, `supabase/migrations/20261101000000_business_portal.sql`). Nobody can change their own role: a trigger keeps it, and only the sign-up trigger and `grant_role()` (database owner only) set it. Make someone an admin from the SQL editor with `select public.grant_role('<profile id>', 'admin');`. On the live project, staff owners and admins from the admin section become admins here too.
- **Signing up and review.** A business signs up with any email address (students still need a university one) and starts as a **pending** business. The UniBuzz team approves, rejects or suspends it on the portal's **Review** page (admins only); approval waits until the owner has confirmed their email.
- **Standing decides access, on every request.** *Pending:* the profile, deal drafts and the team; nothing students see, no listings, no inquiries. *Approved:* everything below. *Rejected:* the owner may fix the profile; nothing else. *Suspended:* nothing. The listings are archived and hidden from students whatever their status says, the deals are paused, and the team's sessions immediately lose the chats (live message events stop too), the listings, deals, numbers and uploads; the portal shows only the suspension. Students keep their chat history with a suspended business but can't write to it.
- **Labels.** "Verified Partner" only for a business an admin verified, with what was checked on record (`admin_set_verified()`; the database refuses the mark without it, and anything but approval clears it). "Sponsored" only for a listing or deal with a **paid promotion** running now: an admin records it on the Review page once it is paid, with the period, the amount and the invoice or receipt reference (`admin_record_promotion()`; nothing else can create one, and payment itself happens outside UniBuzz). Students read the labels through the `listing_sponsored` and `deal_sponsored` computed fields; a business that is neither shows a plain "Business".
- **Listings.** Apartments posted from the portal are ordinary `apartments` rows with `business_id` set, owned by the business's owner whoever on the team posts them. They appear in **Explore › Housing** in the app and on the website with the business's name and logo, its label and no student profile behind them.
- **Deals.** Offers with campus targeting (the universities whose students see them; none ticked means every campus), a start, an optional end and an optional code. Students see live deals of approved businesses on the website's `/deals` page, reached from a link on the Housing page when any exist.
- **Inquiries, never cold messages.** A student messages a business from one of its listings or deals (`start_business_inquiry()`). That opens one chat per student and business, named after the business, with **every team member** in it (later members join it, removed ones leave it). Businesses can't open chats with anyone, can't be messaged directly, can't be added to groups, can't call, and may write in a chat only after the student has, and only while approved. The portal's **Inbox** is the website's Messages (the same two-pane layout, list, chat window, receipts and unread badge) pointed at the portal's own paths: teammates' replies sit on the business's side under their names, and a chat says "Student inquiry" instead of showing the student's activity.
- **Off the student side.** A signed-in business session reads no student content (feeds, comments, likes, roommate posts, items, classes, follows, other listings) and sees only the profiles of its team and of students in its own inquiries; it writes nothing there, never shows or sees who is online or anyone's activity status, and the student website and app send it to the portal. Public pages stay what signed-out visitors always saw.
- **Private details.** Students can read a business's public columns only: the contact email, the admin's review note and the verification evidence are for the team (`my_business()`) and admins.
- **Analytics.** Per listing: views (one per viewer per day; the team's own views don't count), views this week, saves, "Message" taps, inquiries and when its paid promotion ends. Per deal: views and inquiries. The dashboard adds the 30-day totals (`business_listing_stats()`, `business_deal_stats()`, `business_overview()`, readable by a team in good standing and admins only).
- **Team.** The owner invites a colleague by email and passes on the join link the portal shows (`/join/<token>`, valid 14 days, only for that address, only for an address with no UniBuzz account yet). Signing up from it makes a staff account; the invite is used up and the person joins the team **only once they confirm their email** (a trigger on Supabase Auth's confirmation), and only if the invite is still valid, the business still in good standing and the inviter still its owner. Staff see every inquiry and post and edit listings and deals; only the owner edits the business profile and the team.

Checks: `supabase/tests/business-portal.test.mjs` runs every rule above in PGlite (95 checks), and `packages/shared/tests/business.test.mjs` the labels, deal timing and targeting, standings and the team inbox's titles. `supabase/tests/staging/business-portal.mjs` runs the same rules on a real Supabase project through Supabase Auth (real sign-ups and email confirmation, with generated links so no email is sent), the REST API, Realtime (the presence channel, live message events across a suspension) and Storage, then deletes what it made; it refuses the production project:

```bash

```

The staging project (`campconnect-staging`) is built like production: this repo's migrations through 36, the two in `supabase/applied-outside-repo`, then 37 onwards, and the seed.

**Presence (migration 40).** Testing presence on staging showed that Supabase Realtime checks a private channel's join with a broadcast read, so migration 22's presence policy, which allowed only presence reads, refused every join: "Active now" and the green dots stay empty. Migration 40 (`20261102000000_presence_channel_join.sql`) allows reading that one topic for either kind, still only for people who show their status (sending stays presence only, so there are no broadcasts to read); `supabase/tests/presence-channel-join.test.mjs` checks it.

## Video tours (Mux)

Video is the main attraction, so it gets a real pipeline:

- **Upload straight to the provider.** `POST /api/video/uploads` creates a direct-upload URL at Mux and a `media` row; the browser (or the app, with `Authorization: Bearer <token>`) sends the untouched file there in resumable chunks with progress, so a dropped connection resumes instead of restarting. Nothing passes through our server.
- **Processing.** Mux converts the original into adaptive streams (HLS, up to 4K with `video_quality: plus`) and a poster frame. `GET /api/video/{mediaId}` checks the provider and updates the row until it is `ready`; the uploader polls it. Optionally set `MUX_WEBHOOK_SECRET` and `SUPABASE_SERVICE_ROLE_KEY` and point a Mux webhook at `/api/video/webhooks/mux` for push updates.
- **Listings** store a snapshot of ready videos in `videos` (jsonb); a trigger keeps `has_video` in sync. The feed query ranks `has_video` first, then newest, and the "Video tours only" filter uses the same column. Both rules live in the database, not in the web page.
- **Recording in the browser.** "Record a tour" opens the camera with a room-by-room checklist (front door, living room, kitchen, bedroom, bathroom, window view). Phones can also open the camera app directly. Any phone format is accepted, iPhone .mov included, up to 2 GB.
- **Playback.** Feed videos autoplay muted when in view, one at a time, with a shared mute button; detail pages show the video first in the gallery.

Environment: `MUX_TOKEN_ID` and `MUX_TOKEN_SECRET` (Mux → Settings → Access Tokens, Mux Video read + write) on the server only. The `.env.example` lists them. Mux bills per minute stored and delivered.

Add them in the registrar's DNS panel; the site is live on your domain once DNS propagates (minutes to a few hours). HTTPS certificates are automatic.
4. Update `NEXT_PUBLIC_SITE_URL` in Vercel to `https://yourbrand.com` and redeploy.
5. Update Supabase: Site URL `https://yourbrand.com`, add `https://yourbrand.com/auth/callback` to Redirect URLs.

The business portal on its own subdomain (`business.yourbrand.com`): add that domain to the **same** Vercel project (Settings → Domains, then the `CNAME` record Vercel shows), set `NEXT_PUBLIC_BUSINESS_SITE_URL=https://business.yourbrand.com` in Vercel and redeploy, and add `https://business.yourbrand.com/auth/callback` to Supabase's Redirect URLs (`BUSINESS_SITE_URL=https://business.yourbrand.com npm run db:setup` does that with the other auth settings). The proxy (`apps/web/src/proxy.ts`) serves the portal at that host's root and the student pages not at all; until then the portal works at `/business` on the main address.

### Production checklist

- Supabase free projects pause after a week of inactivity; upgrade to the Pro plan (USD 25/month) before real users arrive, which also adds daily backups.
- Supabase's built-in email sender is rate-limited (a few emails per hour). For real sign-ups configure **custom SMTP** (Resend, Postmark, Brevo, SendGrid all have free tiers) under Authentication → Emails → SMTP Settings.
- Keep "Confirm email" enabled so only real mailboxes can sign up. Sign-ups are already limited to the university domains stored on the `universities` table.
- Map tiles come from OpenStreetMap, which is fine for a student site. If traffic grows, set `NEXT_PUBLIC_MAP_TILE_URL` to a MapTiler or Stadia tile URL with your key (both have free tiers).
- Turn on **Vercel Analytics** (free) in the Vercel dashboard for traffic numbers.
- Never expose the `service_role` key in the app. The website only uses the anon key; row-level security does the rest.

## 3. Moving to iOS and Android later

Nothing in the backend has to change, and the shared package already works in React Native: it was verified by creating an Expo SDK 57 app inside a copy of this monorepo, importing `listApartments`, `apartmentSchema`, `formatPrice` and `timeAgo` from `@apartment-book/shared`, type-checking it, and producing a Metro/Hermes bundle. The steps:

1. Scaffold the app inside the monorepo:
   ```bash
   npx create-expo-app@latest apps/mobile --template blank-typescript --no-install
   ```
2. Add these to `apps/mobile/package.json` under `dependencies`, then run `npm install` from the repository root:
   ```json
   "@apartment-book/shared": "0.1.0",
   "@supabase/supabase-js": "^2.115.0"
   ```
   Expo configures Metro for monorepos automatically (SDK 52 and newer). Next.js and Expo both use React 19.2; if npm ever ends up with two React versions (symptom: "Invalid hook call"), pin the same `react` version in both apps.
3. Create the Supabase client the same way as `apps/web/src/lib/supabase/client.ts`, storing the session with `expo-secure-store` (see the Supabase Expo guide), and add the URL and anon key to `app.json` `extra` or an `.env` file.
4. Reuse the shared code in screens:
   ```tsx
   import { listApartments, formatPrice, type ApartmentWithOwner } from "@apartment-book/shared";
   const page = await listApartments(supabase, { universityId, sort: "newest" });
   ```
   Chat uses the same `supabase.channel(...).on("postgres_changes", …)` subscription as `apps/web/src/components/messages/chat-window.tsx`. Three rules learned the hard way, all encoded in `apps/web/src/lib/supabase/client.ts`: set the user's token on the realtime socket before a channel joins (a channel that joins before the session is loaded stays anonymous and row-level security hides every event), give every subscription a fresh channel name, and pass `postgres_changes_options: { wait: true }` so `SUBSCRIBED` means the server is actually streaming. Photo uploads call `uploadImage` with an `ArrayBuffer` read from the picked image (`await fetch(asset.uri).then((r) => r.arrayBuffer())`).
5. Add `"dev": "expo start"` and `"typecheck": "tsc --noEmit"` scripts so Turborepo picks the app up, then ship with **EAS Build**. You will need an Apple Developer account (USD 99/year) and a Google Play developer account (USD 25 once). Push notifications for new messages can be added with Expo Notifications plus a small Supabase Edge Function triggered on message insert.

Until then, the site already works as an installable web app: on a phone, "Add to Home Screen" gives it an icon and a full-screen experience.

## Regenerating database types

`packages/shared/src/types/database.ts` is written by hand to match the migration. If you change the schema, either edit it or generate it with the Supabase CLI:

```bash
npx supabase login

```
